# Спецификация интеграции RAG рецептов

- Status: Implemented
- Дата: 2026-10-19.
- Авторизация: пользователь прямо поручил полную реализацию и интеграцию ранее подготовленного RAG в существующий репозиторий с простым запуском.
- Источник: [дизайн](../../technical/recipe-rag.md). Это поручение разрешает заменить прежнюю обязательную передачу всего каталога на широкий пул кандидатов; full_catalog сохраняется настройкой отката.

## Требования

| ID | Наблюдаемое поведение |
| --- | --- |
| RAG-001 | Поиск объединяет лексические и локальные семантические результаты, возвращая до 10 существующих карточек из Catalog. |
| RAG-002 | Явные исключения продуктов/техники и поддерживаемые пределы применяются до top-k; непонятые условия и недостаток доказательств отражаются в diagnostics. |
| RAG-003 | Отсутствие разметки не доказывает отсутствие аллергена/оборудования; альтернативы техники представлены OR-группами. |
| RAG-004 | Производный индекс вне data привязан к SHA трёх БД, версии документа/признаков и модели. Повреждённый/устаревший индекс пересобирается до readiness. |
| RAG-005 | Backend передаёт актуальный PersonContext; персональные результаты/векторы не хранятся в общем кэше. Исторический dialogue не используется как источник постоянных запретов. |
| RAG-006 | Ограниченный executor удерживает слот до завершения CPU-задачи; deadline даёт честную лексическую деградацию. |
| RAG-007 | Planner получает широкий разнообразный пул с покрытием ролей и расширением при нехватке; расчёты, версии и одна коррекция сохраняются. |
| RAG-008 | Web и CLI используют один модуль. Первый запуск готовит индекс автоматически; CLI поиска/проверки работает без LLM-ключа; запуск приложения доступен одной командой. |

## Контракты

search_recipes получает optional constraints без limit, возвращает recipes и diagnostics с отдельными поисковыми кодами. Generate_plan получает те же optional constraints и передаёт отобранные planning_card генератору. Четыре существующих проверки меню не расширяются универсальной семантической проверкой. Анкета и память учитываются только в поддерживаемой части; остальное остаётся контекстом существующей LLM и явно не сертифицируется поиском.

Новые данные каталога не собираются, исходные БД не меняются. Внешние индексы/веса создаются вне репозитория data. Без доступной модели сохраняется лексический режим с diagnostics; strict-условия не снимаются. Для полного чата/меню по-прежнему необходим OPENROUTER_API_KEY.

## Приёмка

| ID | Проверка | Статус |
| --- | --- | --- |
| RAG-001/002/003 | Контролируемые регрессии отрицаний, релевантности, оборудования, unknown | covered |
| RAG-004 | SHA, повторная сборка, повреждённый индекс, read-only каталоги | covered |
| RAG-005 | Разные профили, очистка памяти, временное условие | covered |
| RAG-006 | Отказ/timeout encoder, занятый worker и отмена | covered |
| RAG-007 | Интеграция Planner, покрытие, отсутствие повторного полного запуска, старые версии | covered |
| RAG-008 | CLI/web, локальный фактический индекс, benchmark и запуск | covered |

Результаты записываются в technical/verification.md и план. Размеченная большая сравнительная оценка моделей и живые LLM-меню требуют отдельного фактического свидетельства: отсутствие ключа не заменяется фиктивным успехом.

## Свидетельства реализации

`uv run pytest -q`: 183 теста, включая 14 сценариев RAG; Ruff lint/format, Python build и TypeScript/Vite прошли. Проверены фактический dense-индекс 693 рецептов, CLI benchmark, 30 задач отбора, авторизованный API, UI-поиск/полный рецепт и запуск `./run.sh`. Live LLM-меню с новой стратегией не вызывалось из-за отсутствия ключа; это ограничение приёмки качества, не заглушка runtime.
