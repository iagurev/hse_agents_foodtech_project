## Состав

[Карта репозитория](repository-map.md) показывает точки входа и путь запроса по модулям.

Один разговорный `Agent` Pydantic AI исполняет штатный цикл модель → инструменты → результаты → ответ. Отдельного supervisor, классификатора намерений, графа ролей и LLM-верификатора нет. Внутренние операции используют короткие вызовы того же SDK без инструментов и собственной автономии.

```text
src/app/
  config.py          централизованные настройки и .env
  assistant/
    agent.py         модель, Agent, персональные инструкции и tools
    tools.py         входы, ответы, описания и обработчики 12 tools + update_memory
    context.py       зависимости текущего хода
    session.py       SDK-цикл, события, журнал и пределы
    compaction.py    история, сжатие и отдельный бюджет
    tokens.py        SDK-сериализация и счётчики Luna/GLM
    __main__.py      CLI для диалога
    prompts/         семь Markdown-ресурсов, включая input_guard.md
  web/
    server.py        FastAPI, авторизация, маршруты и запуск
    contracts.py     типы HTTP-запросов и анкеты
    storage.py       аккаунты, сессии, чаты и текущие версии
    runs.py          фоновые ходы, отмена и SSE
    guard.py         единственный вызов input guard
    presentation.py  безопасная UI-проекция полного журнала
    objects.py       ручные правки без LLM
  models.py          предметные типы
  storage.py         SQLite, версии, история, память, квитанции операций
  catalog.py         рецепты, продукты и FTS5
  planning.py        меню, пересчёт и четыре проверки
  shopping/
    service.py       кэш, подбор SKU, редактирование, ссылки и сохранение
    calculations.py  агрегация, фасовки, стоимость и проверка бюджета
  integrations.py    заменяемый адаптер товаров
  llm.py             ограниченные структурированные вызовы
frontend/src/
  screens/            экраны чата, коллекций, профиля и деталей
  components/         общие элементы, карточки, статусы ответа
  styles/             стили по областям интерфейса
```

Каждый инструмент в tools.py описан одним последовательным блоком: Pydantic-модель входа с `description: ClassVar[str]`, модель результата с `Field(description=...)` и короткий обработчик. Description — метаданные класса: он не становится аргументом или полем JSON. Реестр получает его из аннотации входа обработчика, а SDK строит схему из тех же полей. Описания полей не копируются в docstring или отдельную текстовую схему.

Общие структуры плана, корзины и рецепта определены один раз в соответствующей группе файла. Общие поля результата status, issues и error наследуются от Result; конкретный tool задаёт тип и смысл data рядом со входом. Общие предметные типы переиспользуются из app.models. SDK разворачивает входную модель в плоскую JSON Schema без поля args. У list_plans и list_carts модель пустая: публичный вызов по-прежнему {}. ToolResult[T] проверяет ответ сервиса перед отправкой агенту.

Системный промпт задаёт общие правила диалога, персонализации и выбора действий; значения статусов и ошибок объясняются в description соответствующего инструмента. Второй копии схем в системном промпте нет. Markdown загружается через `importlib.resources`, включая установленный wheel вне корня репозитория. Импорты не открывают БД и не запускают сеть.

Зависимости передаются явно. `Context` не импортирует Agent или Session; короткие обработчики не содержат SQL и алгоритмов покупок. Все definitions остаются в одном `tools.py`: отдельные классы используются только для Pydantic-контрактов, отдельных сервисов или файлов на каждый инструмент нет.

## Модель и протокол

Используются `pydantic-ai-slim[openrouter]==1.68.0`, `openai/gpt-6-luna` через OpenRouter, маршрут `openai` без fallback. `MODEL` и `OPENROUTER_PROVIDER` задают основную модель; `REASONING_EFFORT=medium` — диалог.

- Диалог, генерация/коррекция меню и compaction: Luna `medium`.
- Редакторы плана/корзины и выбор SKU: Luna `low`. Input guard: `google/gemini-2.5-flash-lite` без включённого reasoning, через отдельный GUARD_MODEL и стандартный маршрут OpenRouter. Небольшая живая серия проверяет конкретные случаи, не доказывает отсутствие потери качества на любых запросах.
- Настройки `PLANNING_MODEL`, `PLANNING_PROVIDER`, `PLANNING_REASONING_EFFORT` сохранены. Это ограниченные вызовы одного приложения, а не несколько автономных агентов.
- Native tool calling и структурированные результаты проверены через текущий OpenRouter Chat Completions endpoint. Ограничение direct OpenAI API из официальной карточки не переносится автоматически на этот маршрут; работоспособность подтверждена живой серией, при изменении endpoint нужна повторная проба.
- Каталог, схема, две попытки, четыре проверки и общий RunUsage сохранены. В generate_plan полный каталог получает локальные recipe_id вида r1…rN, назначенные по сортировке постоянных ID. Соответствие неизменно в двух попытках; candidate и feedback остаются в этой системе обозначений. До сохранения известные ID преобразуются обратно. Неизвестные остаются ошибочными ссылками в needs_revision, без угадывания. Поиск и редакторы используют постоянные ID; БД каталога не мигрирует.
- Профиль Luna последовательно применяет штатные `InlineDefsJsonSchemaTransformer` и `OpenAIJsonSchemaTransformer(strict=True)`. Это преобразование тех же Pydantic-контрактов: поддерживаемый `anyOf` вместо `oneOf`, обязательные поля, запрет лишних свойств. Исходные типы и backend-валидация не меняются. Для GLM при явном выборе остаётся прежний профиль.
- `genai-prices==0.0.73` закреплён для совместимости с SDK 1.68.0. Версия 0.1.13 добавляет поле `output_reasoning_tokens`, которое этот SDK не принимает и из-за которого возвращал нулевую статистику.
- SDK `retries=0`, `output_retries=0`, Tool `max_retries=0`, транспорт OpenAI `max_retries=0`. Форматная ошибка не вызывает скрытой дополнительной генерации.
- У генерации меню и каждого редактора максимум два внутренних запроса суммарно: генерация и одна коррекция, включая исправление формата. Неустранённые замечания сохраняются с черновиком; полностью неразбираемый ответ возвращает техническую ошибку.

Ошибочный вызов инструмента останавливает ход без неявной нормализации строк в объекты или третьей попытки. Техническая несовместимость endpoint не выдаётся за плохой рецепт.

## Контекст

| Вызов | Данные |
| --- | --- |
| Разговорный агент | Общий промпт, tools, актуальная анкета и memory, сводка и свежая история конкретного чата |
| Генерация меню | `request`, `days`, явные `limits`, анкета, память, текст диалога, весь каталог planning_card с временными ID r1…rN с уникальными именами ингредиентов без ID, округлёнными числами и предметными ограничениями |
| Редактор плана | Весь current_plan и самодостаточный request; candidate/feedback/fixed_limits при коррекции |
| Редактор корзины | Весь current_cart, request, текущие/явные продукты и до 10 кандидатов FTS, карточки явно названных известных SKU |
| Выбор SKU при plan/recipes | Агрегированные products, top-10 MCP плюс точные SKU-связи каталога, используемые рецепты, контекст, буквальное поисковое уточнение и бюджет |
| Создание из skus | Модель не вызывается: SKU и упаковки напрямую передаются адаптеру ссылки |
| Сжатие | Предыдущая сводка и старые завершённые ходы без reasoning и прежних системных инструкций |

RecipeRetriever используется только для поиска. Генератор получает весь каталог компактных карточек с короткими ID; эти карточки не возвращаются во внешнюю историю. Поиск в чате — отдельная выдача до 10 карточек с постоянными ID, без дополнительных LLM-вызовов. [Рабочий RAG](recipe-rag.md).

Анкета, память и внешние данные маркируются как данные. Предметные промпты учитывают семантику пожеланий; RAG применяет явно поддерживаемую часть условий с диагностикой неизвестности; оставшуюся семантику оценивает модель. Отдельный универсальный семантический валидатор не добавлен.

## История и память

SQLite хранит полный журнал целых ходов. В начале нового хода из копии завершённой истории удаляются `ThinkingPart`; сырой журнал остаётся неизменным. В текущем цикле tools reasoning сохраняет SDK. Системные инструкции и актуальный персональный контекст собираются заново.

Перед каждым запросом, включая продолжение после tools, штатный `history_processors` SDK вызывает контроллер контекста. До 200000 входных токенов история растёт без сжатия. Затем выбирается самый длинный доступный хвост 6 → 3 → 1 → 0 завершённых ходов, который вместе с текущим циклом и резервом сводки 8000 помещается в 200000. Ранее свёрнутые сообщения обратно не извлекаются. Если после удаления всей старой истории остаётся 200000–232000 токенов, запрос разрешён; выше 232000 ход останавливается. Текущий цикл целиком, включая reasoning и результаты tools, не обрезается.

Суммаризатор получает прежнюю сводку и дополнительно исключённые полные ходы; реплики пользователя также собраны в хронологический список `user_messages` для проверки изменений условий. Общая память не меняется. Обычно нужен один вызов, второй допускается для сокращения длинной сводки либо следующего блока истории. Каждый запрос суммаризатора тоже проверяется по размеру; отдельный слишком большой ход не разрывается. Пустой, оборванный или превышающий 8000 токенов итог не сохраняется. Ошибка, timeout или исчерпание двух вызовов останавливают пользовательский ход; промежуточная сводка не публикуется.

Успешная операция атомарно обновляет `summary` и `through_turn`, не удаляя сырой журнал. После этого обновляются инструкции агента и текст диалога для внутренних операций. Для сохранения прерванного хода runtime отличает исторические сообщения по временным меткам `run_id`, а не по прежнему индексу начала новых сообщений.

### Настройки контекста

Все настройки находятся в `src/app/config.py`; переменные окружения имеют те же имена в верхнем регистре.

| Настройка | По умолчанию |
| --- | ---: |
| `context_window_tokens` | 256000 |
| `response_reserve_tokens` | 16000 |
| `token_count_margin` | 8000 |
| `max_input_tokens` (вычисляется из трёх предыдущих) | 232000 |
| `compaction_threshold_tokens` | 200000 |
| `summary_max_tokens` | 8000 |
| `compaction_timeout_seconds` | 180 |
| `compaction_request_limit` | 2 |
| `tokenizer_cache_path` | `data/tokenizer` |

Для чатового агента задан `max_tokens=16000` (SDK передаёт `max_completion_tokens`). Внутренний генератор не получает новый лимит. Luna-счётчик использует tiktoken `o200k_base` и полный JSON подготовленного SDK-запроса с дополнительным запасом на сообщения/схемы. Публичного точного шаблона Luna и её mapping в tiktoken нет: это явная калиброванная оценка, а не официальный токенизатор Luna. Никакого fallback по символам нет; ошибка загрузки останавливает запуск. tiktoken хранит BPE в своём локальном кэше; `TOKENIZER_CACHE_PATH` относится к сохранённому GLM-счётчику. Для явно выбранной GLM остаются закреплённые tokenizers/Jinja2-файлы ревизии `46a050bec13002ad29ee795c16e61cf4fa3c4a9c` с проверкой SHA256.

Оба счётчика переиспользуют SDK-сериализацию сообщений и зарегистрированных схем. Учитываются персональные инструкции и текущий reasoning; непрозрачные reasoning-поля Luna считаются целиком как текст, что может завышать оценку. Загрузка однократная, CPU-подсчёт вынесен в поток. Токенные пределы 200000/232000 и запас 8000 не изменены. В пробах Luna локальный подсчёт составил 6149 против 4928 с tools и 180070 против 174026 на большом входе; это не гарантия достаточности запаса для любого содержимого. При смене SDK/endpoint нужна калибровка. Подробности — в отчёте проверки.


Несколько чатов используют одну анкету и память, но разные историю, сводку и временные условия. `update_memory(text)` заменяет память целиком. Runtime передаёт владельца и версию; SQLite compare-and-swap возвращает `MEMORY_CONFLICT` с актуальной редакцией. Агент объединяет изменение с ней. Удаление памяти не удаляет переписку.

Агент обновляет явно изменившийся устойчивый факт, уточняет прежнюю запись и по просьбе пользователя показывает память для пересмотра. Сам просмотр не вызывает запись. Старые сообщения без нового сообщения пользователя об этих сведениях или их явного подтверждения не служат основанием возвращать забытое. Это инструкции агенту; фоновой очистки, удаления по давности и дополнительного механизма блокировки восстановления фактов в MVP нет.

## Исполнение и остановка

`Session.run` принимает пользовательскую реплику, идентификаторы пользователя/чата и необязательный стабильный `turn_id`. Runtime доверяет авторизации вызывающего приложения; CLI не является многопользовательским HTTP API.

В одном экземпляре Session один чат защищён `asyncio.Lock`. Другие чаты независимы. Это однопроцессное ядро: при запуске нескольких worker-процессов нужна межпроцессная блокировка перед использованием этой гарантии. Независимые чтения SDK может выполнять параллельно; записывающие инструменты помечены `sequential`.

Начальные пределы задачи: 12 модельных запросов и 600 секунд на ход, включая вложенные предметные вызовы; timeout одного запроса — 180 секунд. Compaction имеет отдельные 180 секунд и два вызова на весь пользовательский ход, включая повторные проверки после tools. На время сжатия таймер задачи приостанавливается. Общий `RunUsage` задачи передаётся предметным операциям, статистика compaction учитывается отдельно и добавляется к общим итогам один раз. Отдельной квоты на каталог нет.

История сохраняет новые сообщения, а не повтор всей переписки. При штатной ошибке, отмене или timeout незавершённые call/result пары закрываются результатом сохранённой операции либо `INTERRUPTED`. Уже сохранённые версии остаются доступны. Повтор `turn_id` возвращает прежний ответ; повтор ключа записи возвращает квитанцию без создания второй версии.

Это не обещание crash recovery при принудительном убийстве процесса между модельным вызовом и сохранением хода. Для CLI реализованы обычная отмена и timeout; durable очередь остаётся вне текущего ядра.

События `tool_start`, `tool_end` (с типизированным результатом), `text_delta` передаются необязательному обработчику. Первый текстовый chunk не теряется и не завершает цикл раньше последующего tool call. Reasoning в пользовательские события не отправляется.

Метрики пишутся структурированным Loguru: этап, время, запросы, входные/выходные токены, фактическая стоимость, если её вернул OpenRouter. Неуспешный структурированный ответ также учитывается. Langfuse подключается опционально через отдельный OpenTelemetry provider: один `chat.turn`, нативные SDK-generations/tools и значимые этапы кода. Фактическая стоимость задаётся только на generations; reasoning не суммируется с output повторно. Подключение и дерево описаны в [наблюдаемости](observability.md).

## Уточнение контрактов

Рецепты имеют restrictions и image_url; URL фотографий доступен в поиске и деталях, но не включается во внутренний каталог меню. Поисковые tools не принимают размер выдачи и возвращают до 10 кандидатов. Бюджет передаётся без надбавки, код применяет допуск 5%. Текущий список покупки передаётся один раз как products по product_id. Известные продукты берутся из справочника; неизвестные названия остаются unresolved. Редактирование отделено от создания: полные версии, два вызова максимум, без каталога и неявной подстановки анкеты. Условия новой версии фиксируются перед коррекцией. Кэш sku_records делает найденные товары доступными по ID; product_fts обслуживает локальный поиск новых продуктов внутри edit_cart.

Создание корзины имеет три источника: plan, recipes, skus. Для первых двух request без преобразования добавляется к названию каждого ингредиента; кэш учитывает всю строку запроса. Предварительного разбора покупок нет, shopping_request.md удалён. Для готовых SKU используется только создание ссылки и локальные сведения о цене. Редактор такой корзины возвращает полный список SKU/упаковок, limits и оставшиеся unresolved по SkuCartRevision; null в unresolved сохраняет прежние позиции. Неизвестная цена не блокирует URL и не считается подтверждённым бюджетом.

Отчёт Session содержит вложенный `compaction`: requests, elapsed_seconds, input_tokens, output_tokens, cost_usd. Общие показатели включают его расходы. Логи сжатия содержат размеры до/после, число оставленных ходов, размер сводки и причину остановки; тексты сводки и переписки не журналируются.


## Веб-вызов

HTTP runtime запускает input guard до Session. Он учитывается в общих 12 запросах и 600 секундах; Session получает тот же RunUsage и оставшееся время. Отдельный бюджет compaction не меняется. При отмене Session передаёт внутренний execution_report, чтобы расходы сжатия не потерялись. Этот отчёт не показывается как текст диалога.

Заблокированные и не прошедшие проверку реплики сохраняются с model_visible=0: UI их видит, агент и compaction — нет. Полный протокол сессии, фоновых задач и восстановления описан в [веб-архитектуре](web-application.md).

Внутренний ModelGateway сериализует payload компактным JSON с separators=(",", ":"). Карточки генератора не повторяют служебные пояснения о данных; правило приблизительности цен и времени и смысл пустого restrictions указаны один раз в meal_plan.md. Публичные схемы tools не менялись. [Измерение после реализации](verification.md#компактная-проекция-реализована--2026-10-19).

## Совместимость потокового reasoning

Для закреплённого Pydantic AI 1.68 используется узкий backport [upstream #7214](https://github.com/pydantic/pydantic-ai/pull/7214): части reasoning объединяются по стабильному index провайдера и типу, а не позиции в отдельном chunk. Иначе несколько зашифрованных блоков получали несовместимые ID/signature и следующий запрос завершался 400. Исправление локализовано рядом с build_model; SDK-цикл, сериализация, таймауты и отсутствие скрытых retries сохранены. После будущего обновления SDK backport следует убрать, сохранив протокольный регрессионный тест.

## Исходный ориентир питания

`app.energy.energy_reference` — чистая функция по анкете, без сети и LLM. Разговорный контекст и генерация получают одинаковое energy_reference. EER NASEM 2023: отдельные уравнения по полу, четырём уровням активности и возрастным группам 14–18 / 19+. Для подростков прибавляется 20 ккал на рост. При пропуске активности берётся диапазон всех четырёх сценариев; выбор активности в анкете не подставляется. При недостатке основных данных (например, CLI) возвращается null.

Диапазон вокруг оценки ±10%, округлённый наружу до сотни, — проектное правило удобного подбора, не доверительный интервал и не гарантия индивидуальной точности. Особенно осторожна интерпретация крайних возрастов и физических параметров. Цель похудения/набора не меняет формулу: согласовано, что подбор КБЖУ под цель выполняет агент с учётом диалога, без скрытых фиксированных поправок backend. Явные цели и новые сведения диалога приоритетны. Для подростка не назначается дефицит похудения; обычный ориентир не используется как специальная норма при беременности/лактации/лечебной диете. Эти случаи распознаются семантически по контексту, не новым парсером анкеты.

Промпты объясняют основания, не требуют от пользователя заполнять активность или цели КБЖУ, не перечисляют незаполненные поля в обычном ответе. Итоги сообщаются за день или в среднем за день; неполный рацион не выдаётся за весь дневной рацион. Дополнительного модельного вызова, инструмента или проверки плана нет. Остаются ровно четыре проверки.
