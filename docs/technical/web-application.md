# Мобильное веб-приложение

- Status: Implemented

- Основание: [утверждённая спецификация](../specs/active/mobile-web-app.md).

## Запуск и границы

React/TypeScript/Vite лежит в `frontend/`; FastAPI из `app.web.server` обслуживает `/api` и собранный `frontend/dist`. Команда `uv run meal-app` запускает один процесс на `127.0.0.1:8080`. SQLite общая с CLI. При старте выполняются добавочные миграции runtime и подготовка производного RAG-индекса; исходные рецепты и SKU не импортируются и не изменяются. Без OpenRouter-ключа доступны локальный поиск/просмотр, чат отвечает 503 до создания хода. Встроенной очереди и дополнительных сервисов приложения нет. Несколько workers этим runtime не поддерживаются.

Настройки загружаются через `app.config.Config`; `.env` читается из каталога запуска. Пути данных и frontend задаются явно при запуске вне корня. Wheel включает Python и семь промптов; frontend собирается и поставляется рядом отдельно.

## Аккаунт и контекст

Аккаунт и анкета записываются одной транзакцией после ввода учётных данных и анкеты. Сама анкета состоит из обязательных основных данных и пропускаемого второго шага. Логин 1–64 символа, пароль непустой, хранится Argon2-хеш. Анкета строго проверяет согласованные поля и диапазоны. Необязательные значения остаются null; бюджет в лимиты планировщика backend не подставляет.

Случайный токен сессии живёт 30 дней, в БД хранится SHA256 токена. Cookie HttpOnly, SameSite=Lax, Path=/; Secure включается при HTTPS. Изменяющие запросы отклоняются при чужом Origin или Sec-Fetch-Site=cross-site. Локальные API-клиенты без этих браузерных заголовков допустимы. Каждая операция проверяет владельца сервером. Ответы API имеют Cache-Control=no-store, кроме успешных изображений с частным браузерным кэшем. Публичный deployment, rate limiting и password recovery не входят в этот этап.

## API

Входы описаны Pydantic-моделями в `web/contracts.py`; доменные результаты используют существующий Result. Полная машинная схема доступна в `/openapi.json`, интерактивная — `/docs`.

## Фоновый ход и история

Runs владеет asyncio-задачами, браузер лишь наблюдает. Одна активная задача на чат защищена lock; другие чаты независимы. Состояние и накопленный текст периодически сохраняются в web_runs. SSE передаёт заменяемый снимок, поэтому повтор соединения не дописывает одинаковые фрагменты. Завершившийся ход перечитывается из полного журнала. Переход по вкладкам, reload и закрытие браузера не отменяют задачу.

Состояния: queued → guarding → running → complete/error/cancelled. Отказ guard даёт blocked. При запуске сервера queued/guarding/running становятся interrupted и автоматически не продолжаются. Это восстановление статуса, а не повтор процесса модели. При обычном Stop уже показанный streaming-фрагмент сохраняется в журнал без дублирования завершённых сообщений. На жёстком завершении может потеряться последний ещё не записанный фрагмент текста; сохранённые предметные операции остаются в БД.

Input guard получает текущее сообщение, анкету и два последних разрешённых обмена без tools. Модель `google/gemini-2.5-flash-lite` без включённого reasoning, настраивается через GUARD_MODEL; один PromptedOutput-вызов без tools, retries=0 и output_retries=0. Он проверяет опасные запросы и попытки изменить инструкции, не ограничивает тему питания. При ошибке/timeout агент не запускается. Заблокированная реплика остаётся в UI с model_visible=0 и исключается из истории агента и compaction.

Guard входит в 600 секунд и 12 запросов задачи. Отдельный запрос модели — 180 секунд, guard — 60, товарный HTTP — 60. Compaction отдельно 180 секунд / 2 запроса; токенные границы прежние. Отчёт web_runs сохраняет общие показатели и вложенные guard/compaction; отмена также сохраняет доступный отчёт.

UI читает весь журнал, не сводку. presentation.py пропускает только пользовательский текст, ответы и типизированные результаты tools; reasoning, системные инструкции и сырой JSON не передаются. Карточка в чате сохраняет ID версии из результата. Текст ответа не парсится для восстановления плана/корзины. Удаление чата сначала останавливает его задачу и удаляет его журнал/сводку/web_runs; объекты, память и квитанции предметных операций остаются.

## Этапы работы и время ответа

Прогресс отражает реальные границы кода, не рассуждения модели. Генерация показывает только одну надпись: «Подготавливаю рецепты», «Составляю меню», «Проверяю расчёты», при повторном вызове «Корректирую меню», затем повторную проверку и «Сохраняю меню». Подзаголовков и списка завершённых этапов у генерации нет. Быстрые этапы не задерживаются ради показа.

Корзина показывает агрегацию, поиск товаров, пакетный выбор, расчёт упаковок/стоимости, создание ссылки и сохранение. Поиск считает уникальные продукты после агрегации: completed включает пустые ответы, ошибки интеграции и попадания в кэш; found — только непустые наборы кандидатов. Это ещё не число подходящих выбранных товаров. После поиска остаётся короткая строка его результата. Готовые SKU пропускают агрегацию, поиск и LLM-выбор; пустая корзина не сообщает о создании ссылки.

`Progress` — необязательный получатель событий одной операции, передаваемый из Context в Planner/Shopper. Состояние не хранится в общих экземплярах этих сервисов. Session добавляет tool_call_id к start/end; Runs различает параллельные вызовы, поэтому окончание одного не сбрасывает другой. SSE передаёт текущий progress (name/call_id/stage и completed/total/found), не записывая его в историю модели и не добавляя модельных запросов. Терминальное выполнение очищает активный этап. После reconnect берётся актуальный снимок процесса; перезапуск сервера по-прежнему прерывает ход.

В шапке каждого ответа — одна общая длительность, включая guard, инструменты, compaction и завершающий текст. Сервер считает её монотонными часами; браузер продолжает полученное elapsed_seconds локально через performance.now, без зависимости от синхронизации часов телефона. Таймер обновляется в отдельном компоненте и не вызывает автопрокрутку чата каждую секунду. Формат: «42 с», «1 мин 12 с», «1 ч 2 мин 3 с». После complete/error/blocked/cancelled значение фиксируется; report.elapsed_seconds сохраняется в существующей web_runs без миграции. UI получает только длительность, не полный технический отчёт.

Старые ходы без измерения не получают выдуманного времени. При аварийном перезапуске доступна только последняя сохранённая длительность: она помечается ≥, время простоя сервера не добавляется. Новые таблицы, проценты готовности, прогноз оставшегося времени и генерация статусных сообщений моделью не вводятся.

## Ручное сохранение

URL содержит ID исходной версии; тело — operation_id. Повтор возвращает сохранённый результат, новая доставка устаревшей версии даёт 409. UI удерживает черновик и предлагает открыть актуальный список. Проверка актуальности повторяется внутри транзакции записи. Актуальной считается самая поздняя сохранённая версия всей цепочки, даже если агент редактировал более раннюю ветвь. Предыдущие версии доступны по ID.

План принимает все сохраняемые индексы исходных приёмов и положительные порции. Отсутствие индекса удаляет запись. Добавление/замена через этот API запрещены. Backend пересчитывает КБЖУ и стоимость; сохраняет ровно четыре проверки: recipe_id, числа, сложность, бюджет +5%. Предметные замечания дают needs_revision, форма и API отклоняют некорректные числа. Корзина автоматически не изменяется.

Корзина принимает все сохраняемые SKU с целыми положительными упаковками либо сотыми кг/л для подтверждённого весового товара и индексы сохраняемых unresolved. Она становится независимым источником skus. Существующий снимок SKU используется для расчёта; неизвестная цена остаётся null. Одно нажатие «Сохранить» создаёт одну версию и запросы ссылок по группам до 30 разных SKU. При отказе локальная версия сохраняется, cart_links содержит успешные части и ошибки, link_error объясняет ситуацию. Старые ссылки новая версия не показывает. Нерешённые позиции сохраняются до явного удаления. Для пустой корзины запрос ссылки не нужен.

«Куплено» не меняет магазинную корзину и не создаёт новую версию. При сохранении отметка переносится лишь для того же SKU и того же суммарного количества упаковок. SKU в UI группируются; старые снимки также читаются.

## Проверка

[Отчёт приёмки](verification.md#мобильное-приложение--2026-10-19) разделяет автоматические тесты, реальные модельные вызовы, контролируемые ответы и ограничения Computer Use. Успешная форма корзины не считается подтверждением доступности внешнего магазина.

## Названия, скрытие и карточки

`object_meta` хранит название, скрытие и известное время создания на корне цепочки. Автоматическое меню называется по числу дней исходного плана и дате создания по Москве; старым объектам дата не назначается. Покупка сохраняет название по исходному источнику даже после перехода к самостоятельным SKU. Ручное название имеет приоритет на всех версиях, включая карточки старых сообщений.

Скрытие исключает цепочку из коллекций и list tools, но не удаляет версии, квитанции и ссылки из переписки. Редактирование и создание покупки по скрытому плану разрешены. Скрытие плана не скрывает покупки и наоборот. Архива и восстановления в UI нет.

`project_cards` используется одинаково для SSE и полной истории. Внутри одного ответа выбирается новейшая полученная версия каждой цепочки по хранилищу; пропущенные промежуточные версии не мешают. Более новые версии из других ответов не подставляются. Метаданные названия обновляются независимо от содержимого версии. Финальное SSE-событие отправляется после сохранения состояния выполнения, чтобы перезагрузка и список чатов сразу видели завершённый ход.

## Выбор рецептов и возврат

Результаты `search_recipes` содержат UI-признак выбора и смысл базовой порции. Один рецепт показан один раз в пределах ответа. Выбор и строковое количество хранятся в localStorage по пользователю, чату и ходу; отдельной серверной подборки нет. Начальная порция — 1, допустимы положительные дроби. «Собрать покупки» и «Предложить другое» отправляют обычный видимый текст с точными ID через тот же `/turns`: guard, агент, явные limits, SSE, остановка и расходы остаются общими. Поле ввода не очищается этими кнопками; UI не назначает бюджет. Сетевой повтор использует сохранённый turn_id до успешного подтверждения отправки. Во время активного хода кнопки запуска недоступны.

Существующий hash-router хранит исходный путь в `from`, включая конкретный чат и вложенный переход план → рецепт. Позиции чтения и день плана сохраняются в sessionStorage; выбор рецептов — в localStorage. Прямой переход без `from` возвращает в соответствующую коллекцию. Новая библиотека маршрутизации не требуется.

## Предварительные расчёты

`preview.ts` содержит только чистые расчёты из уже загруженных базовых показателей. При изменении порций/удалении сразу меняются КБЖУ и стоимость блюда, дня и меню; в корзине — строка и итог известной части. Неизвестная цена остаётся неизвестной, неполный итог подписан. Пустое, незаконченное или некорректное количество делает зависимый итог недоступным и блокирует сохранение. Отмена восстанавливает сохранённые значения. Черновик явно отмечен; прежние замечания бюджета не показываются как проверка нового состава. После сохранения окончательны расчёты backend, ссылка меняется только при сохранении.

## Фотографии

UI получает внутренний адрес с SHA256-префиксом исходного URL; сам каталог сохраняет первоисточник. Разрешены HTTPS-изображения `vkusvill.ru` через `wsrv.nl` (ширина 960, WebP) и `images.gastronom.ru` напрямую. Произвольные адреса клиент не передаёт. Один HTTP-клиент живёт в lifespan приложения, отдельного сервиса и хранилища изображений нет.

`IMAGE_TIMEOUT_SECONDS=20` ограничивает всю загрузку, `IMAGE_MAX_BYTES=8388608` проверяется во время чтения, допускаются JPEG/PNG/WebP/GIF/AVIF MIME. Успешный ответ имеет `Cache-Control: private, max-age=86400` (`IMAGE_CACHE_SECONDS`); ошибки не кэшируются. FoodImage показывает заглушку после отказа, без автоматических повторов, и сохраняет корректное состояние уже загруженного фото. Недоступность источника или wsrv.nl остаётся возможной; Gastronom намеренно загружается напрямую.

## Уточнения после пользовательского аудита

Начальная загрузка переписки не затирает оптимистически добавленный первый ход. Ответ позднего GET объединяется с новыми ходами; отписка от SSE не позволяет старому запросу менять другой чат.

Карточки рецептов проецируются одинаково для SSE и reload: если в ответе есть get_recipes, показываются только открытые рецепты, иначе поисковые кандидаты. Текст модели не разбирается. При переходе из меню или подборки URL сохраняет servings; детали показывают соответствующие ингредиенты, КБЖУ и стоимость. Незначимые доли ингредиентов не превращаются в ноль; положительные значения меньше 0.01 показываются как «<0,01».

Блюда одного приёма пищи сгруппированы; дата и действия с именем/скрытием вторичны, итоговые КБЖУ меню раскрываются отдельно. Поля ошибочного количества показывают пояснение, блокируя сохранение; закрытие нижней панели возвращает фокус. Проверены 360/390/430 px; физическая клавиатура телефона и screen reader отдельно не проверялись.

У большой покупки один общий итог и несколько ссылок ВкусВилла с номером части. Сохранение вручную пересоздаёт ссылки по группам до 30 SKU; успешные ссылки остаются видимы при отказе другой. Старый cart_url поддерживается. [Приёмка](ux-audit.md).

## Анкета и ссылки на объекты, 20 октября 2026

Profile.activity: inactive / low_active / active / very_active / null. Старые анкеты без поля продолжают работать; миграция пользовательских данных не нужна. Основные поля остаются обязательными. Пропуск второго шага сохраняет activity/budget/difficulty=null и пустые restrictions. Возврат между шагами сохраняет ввод. В настройках обе группы доступны в одной форме.

POST turns принимает references: [{kind: plan|cart|recipe, id, servings?}]. servings — положительное конечное число только для рецепта. До guard сервер проверяет существование и владельца, разрешает старые и скрытые версии, сам получает название. Название из клиента не принимается. web_runs.references_json добавляется миграцией с [] по умолчанию. Исходный text хранится отдельно от model input: к последнему добавляются проверенные ссылки как данные. Поэтому ID остаются в истории агента, сводке и внутренних операциях, но UI не парсит и не показывает технический хвост. Проекция переписки берёт исходный text из web_runs, ссылки возвращаются также в SSE. Guard проверяет пользовательский текст, заблокированный ход по-прежнему не попадает в историю агента. Повтор того же turn_id возвращает существующее выполнение до повторного разрешения ссылок.

Карточки выбора блюд отправляют ссылки с точными порциями; неотправленный текст композера сохраняется. Поручение из деталей сначала попадает в композер с удаляемой привязкой. Упоминание объекта само по себе не определяет действие. Схемы доменных tools не меняются.

Среднее КБЖУ вычисляется в браузере из totals / days, включая черновик ручной правки. Для незавершённых/неизвестных чисел выводится «—», они не превращаются в нули. Формат хранения и общая стоимость не меняются.

## Трассировка и контейнерный запуск

Новый HTTP-ход оборачивается в `chat.turn` до guard; повтор сохранённого turn_id не создаёт trace. Владелец и чат берутся из серверной сессии. Подробности, закрытый доступ к содержимому и учёт расходов — в [наблюдаемости](observability.md). `LANGFUSE_*` задаются через Config; недоступный exporter не меняет результат задачи.

`Dockerfile` собирает frontend отдельным Node-этапом и Python-приложение с uv.lock; контейнер запускается непривилегированным пользователем. `compose.yaml` содержит один сервис app, read-only data и постоянный runtime-том. Переменные `APP_PORT` и `LANGFUSE_DOCKER_URL` принадлежат Compose; все прикладные параметры остаются в Config. Порядок запуска и сохранность тома описаны в README.
