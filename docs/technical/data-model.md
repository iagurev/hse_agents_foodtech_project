# Данные и каталог рецептов

- Status: Implemented
- Дата: 2026-10-19.
- Основание: согласованное представление данных и уточнения пользователя к контрактам.
- Хранилище: три финальные SQLite каталога и отдельная runtime-БД; модели — `src/app/models.py`, DDL личного состояния — `src/app/storage.py`. [Размещение](data-storage.md).
- Продуктовый контекст: [границы MVP](../design/product.md).

## Нормализованный продукт

Нормализованный продукт — общий ингредиент, построенный на подходящих товарах ВкусВилла и объединяющий бренды, фасовки и несущественные варианты. Правила и фактическое покрытие — в [справочнике продуктов](product-directory.md). Это отдельная запись таблицы `products` с `product_id`, индексируемым названием и полным JSON `payload`.

| Поле | Содержание |
| --- | --- |
| `product_id` | Постоянный идентификатор продукта |
| `name` | Нормализованное название для отображения и поиска SKU |
| `unit` | Одна единица количеств продукта: `g`, `ml` или `pcs` |
| `base_amount` | Количество в этой единице, к которому относятся КБЖУ и стоимость, например 100 |
| `nutrition` | `kcal`, `protein_g`, `fat_g`, `carbs_g` на base_amount; null, если показатели не установлены |
| `cost` | `mean_rub`, `min_rub`, `max_rub` на base_amount; null, если оценка не установлена |
| `restrictions` | Короткий текст существенных ограничений и особенностей продукта; пустой текст не является сертификатом отсутствия аллергенов |
| `conversions` | Необязательные справочные переводы альтернативных единиц: ключ `g/ml/pcs`, значение `{factor, source_url, note}`; одна альтернативная единица равна factor единицам продукта. Это оценка, а не маркировка конкретного SKU |

Например, 250 мл молока — ссылка на запись молока с unit=ml и amount=250. КБЖУ и цена в самой записи могут относиться к 100 мл. Масса и объём не считаются равными автоматически. Единицу существующего product_id нельзя менять при повторном импорте: это изменило бы смысл количеств сохранённых рецептов и корзин.

Продукты входят в финальную БД products.sqlite. Агент не добавляет новые записи. Если при редактировании ингредиентов назван продукт вне справочника, он попадает в нерешённую часть покупки. Похожие названия не являются достаточным основанием считать продукты взаимозаменяемыми. Несовместимые варианты должны иметь разные product_id или требовать согласованной замены.

## Рецепт и карточка

Рецепт — конкретный способ приготовления. Отдельный слой «блюдо» отсутствует. Карточка — компактная проекция того же recipe_id.

| Поле полной записи | Содержание |
| --- | --- |
| `recipe_id`, `title` | Постоянный ID и понятное название |
| `ingredients` | Ссылки `{product_id, amount}` на нормализованные продукты; количество в unit продукта на базовую порцию рецепта |
| `meal_roles` | Подходящие приёмы пищи |
| `difficulty` | `easy`, `intermediate`, `advanced` |
| `active_minutes`, `total_minutes` | Активное и полное время |
| `equipment` | Необходимая техника и принадлежности |
| `base_serving` | Что означает одна базовая порция |
| `nutrition` | КБЖУ базовой порции |
| `cost` | Средняя цена и диапазон цены базовой порции |
| `restrictions` | Одно короткое описание: при каких ограничениях рецепт не подходит и какие существенные особенности нужно учесть |
| `steps` | Инструкции приготовления |
| `source_url` | Первоисточник; для авторской адаптации — источник вдохновения |
| `image_url` | URL фотографии, null только если источник не предоставил изображение |

Публичная карточка не содержит steps и source_url; ингредиенты раскрываются как product_id и название без количеств. Для внутреннего генератора используется отдельная planning_card: полный каталог, ingredients как уникальные полные названия с сохранением порядка, без ID продуктов и фотографий. Из restrictions удаляются известные служебные пояснения о происхождении/пересчёте/партии, предметные ограничения и неопределённость аллергенов сохраняются. Служебные сведения остаются в полном рецепте и источниках. Полный рецепт для агента раскрывает ингредиенты как product_id, name, amount, unit.

КБЖУ базовой порции рецепта округляются ROUND_HALF_UP до целых и записываются целыми JSON-числами; средняя/минимальная/максимальная цена — до копеек. Это правило Recipe, включая сохранение в recipes.sqlite; исходные маркировки продуктов и SKU, доказательства и дробные количества ингредиентов/порций не округляются. Проверка арифметики допускает только погрешность квантования 0.5 для КБЖУ и 0.005 рубля для цены, плюс 1e-8 на машинную арифметику. Проверенная исходная рецептура сравнивается после того же округления, другие поля должны совпадать.

Полей techniques, composition, estimates и provenance в рецепте и выдаче нет. Вместо набора тегов — текст restrictions. Например: «Содержит молоко, яйца и пшеничную муку; не подходит при их исключении. Время предполагает сухой творог; отцеживание влажного добавляет 4–6 часов». Текст сравнивает с контекстом модель; код не вводит дополнительные проверки аллергенов или предпочтений. Числовые ограничения сложности и бюджета остаются отдельными полями.

Нормализация, дедупликация, разметка ограничений и подготовка показателей выполняются до диалога. Нет отдельного обязательного summary. КБЖУ и цена рецепта относятся к установленной порции, не к упаковке магазина.

## Поиск и подготовленный каталог

Каталог находится в трёх финальных SQLite: `data/recipes.sqlite`, `data/products.sqlite`, `data/sources.sqlite`. Приложение открывает их только для чтения; все файлы имеют версию схемы и общий ID выпуска. JSON-импорт и DTO PreparedCatalog удалены из runtime. Подготовка, включая прежнюю проверку атомарного импорта, хранится в отдельном архиве. [Схемы, архив и проверка](data-storage.md).

Рабочий поиск объединяет лемматизированный FTS5 и локальные семантические векторы, применяя явный RecipeSearchLimits до top-10; query не разбирается на условия. Производный индекс вне data проверяется по SHA трёх БД. Выдача — до 10 карточек; диагностика остаётся внутренней, анкета/память не подставляются. Старый FTS5 используется только при явном отключении RAG. Детали возвращают найденные рецепты, пропуская неизвестные и повторные ID.

Внутренний generate_plan получает весь каталог компактных карточек с временными короткими ID; RAG участвует только в поиске. Edit_plan получает текущий план и поручение; рецепты для пересчёта читаются по постоянным ID. Четыре проверки меню сохранены. [Контракт RAG](recipe-rag.md).

## SKU и покупки

SKU — конкретный товар магазина: `sku_id`, `title`, `price_rub`, `package_amount`, `package_unit`, `source_url`, `composition`, `package_basis`. Поле composition у SKU — текст состава внешнего магазина; удаление composition из рецепта его не затрагивает. Неизвестные сведения остаются null. Фасовка из названия явно отмечена источником, неизвестная масса не угадывается.

Корзина хранит источник, `products`, выбранные `items`, `unresolved`, стоимость, полноту результата, ссылку и ошибку создания ссылки при наличии. Отдельной сущности Need и отдельного need_id нет.

- `products`: `{product_id, amount, recipe_ids, requested_sku_id}`. Количество выражено в unit справочника, null означает неизвестное количество. recipe_ids сохраняют назначение, при создании requested_sku_id задаёт явный выбор, после редактирования также хранит сохранённый выбор исходной позиции.
- `items`: `{product_id, sku_id, product, packages}`. В product находится карточка SKU, packages вычисляет код для ингредиентов или принимает явно для готовых SKU. Для прямых SKU product_id=null; product=null, если карточки нет в кэше. Прежние записи без внешнего sku_id читаются по product.sku_id.
- `unresolved`: `{product_id, recipe_ids, reason}`. Для названия вне справочника product_id=null, причина содержит исходное название. У известного продукта назначение сохраняется даже при провале SKU-поиска.

Создание покупки:

1. Для plan/recipes получить product_id и количества из рецептов с учётом порций.
2. Сложить количества одного product_id. Неизвестное количество не превращается в ноль; разные требования к конкретному SKU не склеиваются молча.
3. Для каждого продукта получить до 10 кандидатов SKU из кэша или внешнего поиска. Query — название плюс неизменённый request, если он непустой.
4. Если есть кандидаты, одним модельным вызовом выбрать SKU для всех продуктов с учётом контекста.
5. Кодом рассчитать упаковки и стоимость, проверить бюджет и получить ссылку для найденной части.
6. Сохранить новую версию, включая нерешённые продукты.

Кэш хранит кандидатов, не персональный окончательный выбор. Ключ — SHA256 полной буквальной строки query (название и request), TTL 24 часа; промахи выполняются с параллельностью до четырёх. Предпочтения и текст ограничений учитываются при выборе кандидата. LLM-разбора запроса нет. Request — короткое общее поисковое уточнение; он не меняет ингредиенты и количества. Редактирование использует отдельный полный CartRevision без повторного выбора SKU.

Внешние search_products и get_product_analogs также возвращают до 10 кандидатов без аргумента размера. Поиск не меняет корзину. Создание ссылки не оформляет заказ.

## План, версии и бюджет

План хранит относительные дни, приёмы пищи, recipe_id и servings, пояснение, рассчитанные totals и daily, исходные limits и request. Поля feasible нет. Дата начала и количество людей отсутствуют. Полные инструкции и каталог в план не копируются.

Агент передаёт исходный budget_rub без прибавки. Код проверяет верхнюю границу round(budget_rub × 1.05, 2). Экономия допустима. Для плана сравнивается средняя оценка ингредиентов, для корзины — цена найденных упаковок. Диапазон стоимости в карточке и фиксированный допуск проверки — разные вещи. Код не добавляет нижнюю границу расхода.

План и корзина независимы. Каждая запись создаёт новый ID и parent_id; предыдущая версия остаётся доступной. Неуспешное изменение не затирает успешную версию. В одной транзакции сохраняются объект и квитанция операции. Статусы, ошибки и четыре проверки описаны в [контрактах](tool-contracts.md).

## Чаты и персональный контекст

Анкета и память принадлежат пользователю; история и сводка — чату. Временные исключения одного чата не попадают в другой. План и корзина доступны по ID с проверкой владельца. Сводка не становится общей памятью. Политика истории — в [harness](agent-harness.md).

Recipes/recipe_fts хранятся в финальной БД рецептов; products/product_fts/product_directory/product_skus/product_aliases — в БД продуктов; catalog_skus — в БД исходников. sku_cache, sku_records, objects, operations, users, chats и turns принадлежат отдельной runtime-БД. Приложение не импортирует и не мигрирует финальные каталоги при запуске; initialize относится только к личному состоянию. Перенос сохранил все личные таблицы без изменений.

## Стартовые данные

Рабочий каталог использует 825 полных общих продуктов, семь служебных записей совместимости и подготовленные рецепты. Дополнительно сохранён ID колы с nutrition=null, без участия в активном поиске. Новые адаптации строятся только из активных категорий с полными КБЖУ и ценой. 230 неполных категорий и 555 SKU с незавершённой классификацией сохраняются отдельно; ещё шесть классифицированных SKU колы относятся к отложенной категории и не входят в принятые связи. [Актуальная очистка](catalog-rag-readiness.md), [выпуск рецептов](catalog-cleanup.md), [справочник](product-directory.md), [данные](data-storage.md).

Показатели готовой категории относятся к одной физической базе. Цена — средняя нормализованных наблюдений снимка 17.10.2026 с фактическим min/max; КБЖУ — агрегат маркировок, в отдельных случаях явное дополнение ВкусВилла с сохранённым происхождением. Доля наблюдений и диапазоны доступны приложению; это не точный состав каждого SKU. При отсутствии подтверждённых данных новая категория остаётся в подготовке.

КБЖУ и стоимость четырёх прежних рецептов в этой миграции не пересчитывались. Их редакторские оценки и история исходной подготовки остаются в `sources.sqlite.reports` под ключом `data/recipe-estimates.json` (также в архиве). Семь служебных продуктов сохраняют прежние показатели и единицы, не включаются в новый поиск и не объявляются полностью обогащёнными из ВкусВилла.

## Редактирование и добавленные индексы

PlanRevision расширяет существующий PlanDraft полями days и limits. CartRevision использует существующие CartProduct и формат unresolved, добавляя limits. Это полные версии, не операции изменений. Метаданные и вычисляемые поля формирует backend.

Ограничения исходной версии сохраняются, пока request явно их не меняет. При коррекции backend использует копию limits первого разобранного ответа, игнорируя попытку изменить их в исправлении. Полнота исполнения текстового поручения остаётся модельной задачей.

`product_fts(product_id, name)` — сохранённый FTS5-индекс в финальной БД продуктов. Приложение его не перестраивает при запуске. Редактор получает текущие и явно названные ID плюс до 10 результатов поиска по тексту; префиксы длинных слов помогают простым русским словоформам. В управляемом справочнике индекс включает 5522 канонических имени и алиаса; сложные словоформы и семантические замены всё ещё не гарантируются. Служебные прежние записи доступны по сохранённой ссылке, но не индексируются для нового выбора.

`sku_records(sku_id, payload, updated_at)` — последние фактические карточки из поиска, аналогов и внутреннего подбора. Содержит общедоступные сведения SKU, не пользовательские корзины и предпочтения. Поисковый кэш кандидатов sku_cache с TTL 24 часа сохраняется отдельно. Для неизменённой позиции редактор использует её прежний снимок; для нового SKU — запись sku_records. Проверка наличия и автоматическое обновление снимков не добавляются.

SKU-кэш добавляется через initialize пользовательской runtime-БД без удаления объектов и истории; product_fts принадлежит отдельной финальной БД продуктов. Существующие корзины доступны без предварительного заполнения SKU-кэша: их карточки уже находятся в items. При подборе SKU под ингредиент неизвестные новые SKU остаются unresolved до получения достоверных данных поиском. Для прямой корзины количество уже задано в упаковках: карточка необязательна для ссылки, а цена остаётся неизвестной.

## Прямой источник SKU

Публичный CartSource принимает plan, recipes или skus. SkusSource.items содержит sku_id и положительное целое packages, по умолчанию 1. Дубликаты суммируются перед ссылкой. Нормализованные продукты не требуются: products и unresolved пусты, items содержит явные SKU и доступные карточки из кэша. SKU не создаёт записи справочника продуктов.

subtotal_rub — сумма позиций с известной ценой, null при отсутствии цен или переполнении. total_is_complete подтверждает подбор и известность цен всех позиций, но не создание ссылки. При неизвестной цене статус partial, даже если ссылка уже есть; соблюдение полного бюджета не подтверждено. При превышении бюджета известной частью — needs_revision. Отказ ссылки сохраняется отдельно.

Редактор SKU-корзины использует SkuCartRevision(items, limits), сохраняет неизменённые снимки, пересчитывает цену и создаёт новую ссылку. StoredCartSource отдельно разрешает прежний text только в сохранённых объектах. Миграции и пересоздания БД для этого изменения не нужны.


## Подготовка крупных снимков

Контракт PreparedCatalog и публичные модели сохранены. Все исходные рецепты учитываются в `sources.sqlite.recipe_sources` и `recipe_preparation`; прежний `data/preparation/enrichment.sqlite` архивирован; неполные записи остаются вне runtime-каталога. Нормализованные продукты с неизвестными КБЖУ/ценой используют разрешённый null. У используемых записей сохраняются ID и unit; канонические показатели обновляются из SKU, служебные записи сохраняют прежние показатели для совместимости. Первый проход использовал полное имя ингредиента и одну наблюдаемую единицу. Теперь подготовка использует сохранённые категории SKU и их алиасы; неизвестная конверсия блокирует готовность ингредиента, а не меняет число.

Товарный снимок сохраняется отдельно в исходном MCP-формате, включая вложенные price, weight, properties, images и category. Служебные поля наблюдений не подмешиваются в исходную карточку. [Методика и приёмка](catalog-enrichment.md), [данные и отчёты](data-storage.md).

## Происхождение продуктового справочника

`product_directory(product_id, evidence)` хранит SKU, наблюдения цены/КБЖУ и их базы. `product_skus(product_id, sku_id)` связывает общий продукт с конкретными товарами. `catalog_skus(sku_id, payload)` содержит все 7492 исходные JSON-карточки MCP без адаптации; это отдельный слой от live `sku_records`. `product_aliases(alias, product_id)` хранит разрешённые поисковые имена готовых категорий. Внутри файла связи имеют внешние ключи. Межфайловые recipe→product и product_sku→catalog_sku проверяются `app.catalog_check`: SQLite не поддерживает FK между attached-базами.

`Catalog.product_sources(product_id)` и `Catalog.source_skus(product_id)` доступны внутренним потребителям; поля NormalizedProduct и публичные tools не изменены. Первая полная миграция применяется отдельной командой с backup, очисткой прежних прототипов и сохранением всех используемых ID. Рабочий Catalog только читает три базы; прежние import_file и скрипты миграции находятся в архивном снимке.

Текущий выпуск описан в [catalog-cleanup](catalog-cleanup.md): все 2508 источников рассмотрены от очищенного справочника, окончательный реестр хранится в `sources.sqlite.recipe_preparation`, а файлы `data/recipe-adaptation/` перенесены в архив. Пользователь разрешил новые редакторские граммовки и порции в явно обозначенных авторских адаптациях. Граммы не объявляются измерением исходных штук/ложек. Каждый вариант имеет свой ID и согласованные инструкции; исходник, сопоставления, исключения, кулинарные проверки и новые рецептуры сохранены отдельно. КБЖУ и стоимость новых вариантов в точности пересчитываются из активных продуктов runtime. Ingredients/nutrition/cost относятся к одной base_serving. В шагах нет дублирующих количеств ингредиентов: сохраняются метод, время, температура, размер изделий и распределение между этапами; UI пересчитывает список ингредиентов на выбранные порции. Числовое время берётся из исходника как ориентир метода, не объявляется замером адаптации; явные противоречия блокируют выпуск. Отдельный отбор 13 категорий и 15 новых карточек в `data/recipe-rebuild/` относятся к предыдущему этапу.

## Хранение при compaction по токенам

Схема БД не изменяется. Полные `turns.messages` остаются в журнале; успешная операция одной транзакцией обновляет только `chats.summary` и `chats.through_turn`. Промежуточные сводки не записываются. Выбор хвоста читает лишь ходы после границы; старые сообщения ради шести ходов не восстанавливаются. Сводка относится только к чату и не обновляет memory пользователя. Временные run_id исторических сообщений используются в проекции SDK для отделения текущего хода и не переписывают исходные записи.

## HTTP-приложение и версии (19.10.2026)

Добавочные миграции WebStore сохраняют существующие данные. Новые таблицы: accounts (user_id, уникальный login, password_hash), sessions (token_hash, user_id, expires_at), chat_meta (chat_id, title, updated_at), web_runs (chat_id + turn_id, text, state, output, report, created_at, references_json), purchased (object_id + sku_id). В turns добавлен model_visible с default=1. Схемы рецептов, нормализованных продуктов и SKU не менялись.

Полный журнал сохраняется независимо от сводки; model_visible=0 исключает заблокированные запросы и ошибки входной проверки из модельного контекста. Старые строки получают 1. Web_runs восстанавливает UI-состояние и идемпотентность запуска; незавершённые при рестарте помечаются interrupted.

Индекс objects(parent_id) и рекурсивный запрос определяют последнюю сохранённую версию всей цепочки. Ручная запись проверяет актуальность внутри BEGIN IMMEDIATE, повтор operation_id возвращает прежний Result. Исторические карточки ссылаются на точный ID версии. Purchased переносится лишь при совпадении SKU и количества упаковок.

Ручная корзина сохраняет источник skus, включая допустимый пустой список в **сохранённой** модели StoredSkusSource; публичный create_cart по-прежнему требует непустой список SKU. Unresolved остаётся частью корзины. Прямой редактор сохраняет его, если новое содержимое не задано явно. Больше деталей — [HTTP runtime](web-application.md).

## Размещение файлов после очистки

Личные таблицы Store/WebStore и живые sku_cache/sku_records находятся в `../hse_agents_runtime/assistant.sqlite`. Три финальные БД data не содержат пользователей, сессий, объектов или переписки. Recipes/FTS — в recipes.sqlite, продукты/evidence/алиасы/связи — в products.sqlite, native SKU/исходные рецепты/документы/реестр подготовки — в sources.sqlite. `Catalog.source_document(reference)` читает документы по прежнему пути как ключу БД, не обращаясь к файловой системе. Полный источник — [data-storage](data-storage.md).

### Единицы продажи SKU, 2026-10-19

Product.sale_unit: kg/l для подтверждённой продажи за кг/л, null для упаковки. price_rub относится к этой единице; package_amount=1000 г/мл у весового SKU. packages теперь число единиц продажи: положительные целые упаковки либо дробные кг/л с шагом 0.01. Backend проверяет соответствие карточке, поэтому неизвестная карточка разрешает лишь целые упаковки. Имя поля и существующие записи сохраняются. При чтении прежних Product точная метка package_basis «Единица продажи MCP: кг/л» восстанавливает sale_unit без миграции сохранённых объектов. UI показывает кг/л и допускает десятичный ввод при ручной правке.

Каталог и исходные SKU не переписываются. Фасовка дополняется только у найденного SKU с неизвестным package_amount, при единственном согласованном наблюдении price_observations в принятой product_skus-связи. Противоречия не разрешаются догадкой. Явные package_observations исправляют прежние неподходящие фасовки; conversions позволяют расчёт г↔мл/pcs только с сохранённым источником оценки. Кандидаты дополняются принятыми product_skus-связями; цена и дата живого ответа при совпадении SKU важнее снимка. Внутренний purchase содержит рассчитанную покупку для выбора SKU; в сохранённой корзине вычисляемые поля не дублируются. Расчёт бюджета плана не меняется.


### Метаданные цепочек, 2026-10-20

`object_meta(root_id, title, hidden, created_at)` добавляется к runtime: один ряд на корень `objects`, FK к объекту. При миграции существующие корни получают title=null, hidden=0, created_at=null; неизвестная дата не восстанавливается догадкой. Новый корень получает время в транзакции сохранения, дочерние версии наследуют общие метаданные через рекурсивный запрос. Payload версий, operations и turns не переписываются.

Скрытие применяется только при перечислении; get/edit/create_cart по существующему ID сохраняются. Для UI `root_id/title/hidden` накладываются на результат отдельно от доменной схемы. Порядок сохранения объектов используется для выбора последней из версий, полученных в одном ответе, включая разветвления и пропущенных предков. Исходный payload корня определяет автоматическое название покупки после ручного преобразования её источника в SKU.

## Дополнения пользовательского аудита, 20 октября

Product хранит `price_source` и `price_observed_at`. Каталожная дата берётся из metadata.snapshot_date, кэш MCP сохраняет дату поиска (для старого кэша — его updated_at), чтение не делает цену свежей. В позиции корзины `quantity_basis` сохраняет использованный справочный коэффициент либо null. Текущие оценки: съедобная часть яйца 50 г/шт, рафинированное растительное масло 0.96 г/мл, молоко 1.03 г/мл; точные источники и оговорки записаны в products и evidence.

`cart_links` — части одной покупки: `{sku_ids, url, error}`. До 30 разных SKU на часть; дубли SKU агрегируются до разбиения. Общая стоимость и состав остаются в одном объекте. Отказ части сохраняет её SKU и ошибку, успешные ссылки доступны. `cart_url` сохраняется для совместимости при единственной части; при нескольких — null. Старые объекты без cart_links читаются через cart_url. Миграция личной БД не нужна: поля добавлены в payload новых версий.

В questionnaire добавлена nullable activity (inactive/low_active/active/very_active), старые анкеты без поля допустимы. references_json хранит проверенные ссылки на версии с названиями и необязательными порциями; исходный text предназначен для UI, модель получает ссылки отдельным разделом своего пользовательского сообщения. energy_reference вычисляется из анкеты при формировании контекста, не записывается как пользовательская цель.
