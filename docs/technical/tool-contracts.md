# Контракты инструментов

- Status: Implemented
- Дата: 2026-10-18.
- Основание: согласованный список инструментов и уточнения пользователя к аргументам, проверкам и обработке результата.
- Область: работающие сигнатуры, Pydantic-схемы, descriptions и результаты. В `src/app/assistant/tools.py` каждый tool расположен одним блоком: входная Pydantic-модель с description инструмента и Field-описаниями аргументов → модель ответа с типом и описанием data → обработчик. Description задан как ClassVar и не входит в JSON. Общие вложенные структуры определены один раз и переиспользуются; общие предметные типы находятся в `src/app/models.py`. Развёрнутых копий схем в docstrings нет.

## Общие правила

Агент видит 12 доменных инструментов и служебный `update_memory(text)`. Агрегация, расчёты, кэш, проверки и создание ссылки — внутренние функции, не дополнительные инструменты агента. Объекты `Tool` и их подключение описаны в [архитектуре](agent-harness.md).

`user_id`, права доступа, настройки, клиенты, анкета и память передаются через runtime-контекст. Пользовательский ID не выбирается моделью. Выбираемые `plan_id`, `cart_id`, `recipe_id` и `sku_id` остаются аргументами. Эти пространства идентификаторов не взаимозаменяемы.

`limits` — явный аргумент создания плана и корзины. Агент учитывает анкету и текущий диалог; backend не заполняет пропущенные поля. У edit_plan и edit_cart аргумента limits нет: ограничения находятся в исходном объекте и сохраняются, пока request явно не меняет конкретное значение или не снимает его. Редактор возвращает ограничения новой версии; при коррекции код фиксирует их по первому разобранному результату. Из анкеты редактор ничего не наследует.

Поисковые инструменты возвращают до 10 кандидатов. Аргумента `limit` у агента нет. Знак `?` в таблице означает необязательный аргумент, а не скрытое наследование условий.

После generate_plan меню уже доступно пользователю в типизированной карточке. Описание инструмента рекомендует короткое подтверждение; для запрошенного подробного обсуждения агент получает рецепты через get_recipes. recipe_id не является названием блюда, и таблица ID не заменяет пользовательское меню. Схемы входов/выходов этим уточнением не меняются.

## Сигнатуры

Входы и выходы заданы отдельными Pydantic-типами с Field(description=...). Один входной объект SDK разворачивает в плоскую схему: дополнительного args в JSON нет. List-инструменты используют пустые модели без полей и по-прежнему принимают {}. Ответы проходят проверку ToolResult[T] перед отправкой агенту. Схема результата описывает контракт кода; в native tool definition SDK передаёт схему аргументов, а смысл результата объясняет description инструмента.

| Инструмент | Сигнатура | Результат |
| --- | --- | --- |
| Список планов | `list_plans()` | `PlanListResult` |
| Получение плана | `get_plan(plan_id)` | `PlanResult` |
| Создание плана | `generate_plan(request, days, limits, constraints?)` | `GeneratePlanResult` |
| Изменение плана | `edit_plan(plan_id, request)` | `EditPlanResult` |
| Поиск рецептов | `search_recipes(query, constraints?)` | `RecipeSearchResult` |
| Детали рецептов | `get_recipes(recipe_ids[])` | `RecipeDetailsResult` |
| Создание корзины | `create_cart(source, limits, request?)` | `CartResult` |
| Список корзин | `list_carts()` | `CartListResult` |
| Получение корзины | `get_cart(cart_id)` | `GetCartResult` |
| Изменение корзины | `edit_cart(cart_id, request)` | `EditCartResult` |
| Поиск товаров | `search_products(query)` | `ProductSearchResult` |
| Аналоги товара | `get_product_analogs(sku_id)` | `ProductAnalogsResult` |

У `list_plans()` и `list_carts()` нет даже необязательных аргументов. В протоколе вызова передаётся `{}`. Они возвращают краткие метаданные всех объектов текущего пользователя в MVP; без `limit`, `cursor` и скрытого усечения. Полное содержимое получают через `get`.

`start_date` и `people_count` не входят в генерацию и не восстанавливаются из контекста как неявные параметры. Дни относительные, количества выражаются порциями рецептов.

## Планы

`generate_plan` получает запрос, количество дней, явные ограничения и персональный контекст. Один внутренний LLM-вызов выбирает рецепты и порции из широкого RAG-пула карточек (full_catalog сохранён настройкой отката). Код пересчитывает КБЖУ и стоимость, выполняет четыре проверки и при необходимости передаёт замечания на одну попытку исправления.

Успешный план сохраняется и получает `plan_id`. Если замечания остаются, сохраняются адресуемый черновик и замечания. Во внешний чат возвращается компактный результат; полный каталог не возвращается.

`edit_plan` загружает полный текущий план по ID и передаёт его отдельному редактору с самодостаточным request. Основной агент заранее выбирает новые рецепты и указывает их ID, нужные дни/приёмы пищи и порции; ссылки вроде «второй вариант выше» раскрываются. Внутренний ответ PlanRevision содержит все meals, days, limits и explanation. Каталог, анкета и история редактору не передаются. Backend получает выбранные рецепты по ID, выполняет те же расчёты и четыре проверки, сохраняет полную новую версию. Ошибка не уничтожает предыдущую; оставшиеся замечания дают адресуемый черновик. Корзина автоматически не перестраивается.

`get_plan` возвращает содержимое, выбранные рецепты и порции, рассчитанные показатели, применённые ограничения и состояние. Полные инструкции рецептов доступны через `get_recipes`.

Descriptions поясняют `totals`/`daily`, `issues` и `explanation`: отсутствие числовой цели не отключает расчёт КБЖУ; замечания проверок и причины неудавшегося составления меню возвращаются в результате. Разговорный агент кратко передаёт фактический результат без обязательного сценария пополнения каталога и без раскрытия технических кодов, если пользователь их не запрашивал.

## Рецепты

`search_recipes` — поиск по одному конкретному запросу в собственной подготовленной базе. Например, запрос может описывать рецепт, блюдо или желаемое сочетание продуктов. Результат — `data.recipes` и `data.diagnostics` с неизвестными условиями и деградацией; score и embeddings не возвращаются. Optional constraints содержит действующие исключения продуктов/техники, время, сложность, роли, diet и allergens. Backend добавляет актуальные анкету/память; пустой явно переданный список снимает прежний запрет для задачи. Поиск не создаёт план и не загружает новые рецепты из интернета в рамках обычного вызова.

Пустой результат означает, что по запросу в базе ничего не нашлось. У близких вариантов агент кратко отмечает существенные отличия от запроса; отдельный сценарий обработки отсутствующих рецептов не вводится.

`generate_plan` самостоятельно получает широкий RAG-пул с расширением до всего допустимого каталога при нехватке покрытия до первого вызова модели. Full_catalog сохраняется настройкой отката. Пустой подтверждённый пул даёт NO_SUITABLE_RECIPES; после неудачной генерации полного перезапуска нет. `edit_plan` каталога не получает: выбор новых рецептов делает разговорный агент через обычный поиск или известные ID до вызова редактора. Физический отказ API по размеру контекста остаётся технической ошибкой.

`get_recipes` получает один или несколько ID в массиве и возвращает `data.recipes` с полными существующими записями и фотографиями. Неизвестные ID пропускаются без дополнительного поля; дубли входных ID устраняются. Пакетное получение не требует отдельного генеративного вызова на каждый рецепт.

## Корзины и товары

`source` в `create_cart` задаёт один из трёх источников:

```text
{type: plan, plan_id: "p_123"}
{type: recipes, items: [{recipe_id: "r_42", servings: 2}]}
{type: skus, items: [{sku_id: "sku_42", packages: 2}]}
```

Это иллюстрации вариантов данных, не JSON Schema. Для plan/recipes инструмент получает ингредиенты и количества из рецептов. Request — короткое поисковое уточнение, применимое к каждому продукту, например бренд. Код добавляет его буквально к названию продукта через пробел; отдельного LLM-разбора нет. Request не меняет количества или состав и не предназначен для истории диалога, списка покупок, бюджета, исключения продуктов или инструкций редактору. Без такого уточнения он пустой.

Для skus передаются конкретные sku_id и целые положительные packages (по умолчанию 1). Повторы SKU суммируются; вызывается создание ссылки без поиска и модели. Request должен быть пустым, иначе INVALID_CART_REQUEST. Сведения из кэша используются для цены и отображения; отсутствие карточки не блокирует ссылку, но полная стоимость и соблюдение бюджета не подтверждаются. Для покупки по свободному тексту разговорный агент сначала ищет товары и выбирает SKU, затем вызывает этот путь. Текстовый source удалён из новой схемы; чтение и редактирование ранее сохранённых корзин поддерживаются.

После агрегации по `product_id` для каждого продукта извлекаются до 10 кандидатов из кэша или поиска. Все кандидаты передаются одним пакетом на выбор SKU. Если есть кандидаты, выполняется один LLM-вызов выбора; попадание в кэш кандидатов не отменяет этот этап. Результат содержит `cart_id`, позиции, упаковки, стоимость, нерешённые потребности и ссылку, когда она создана. Создание ссылки не оформляет заказ. Ссылка создаётся и для найденной части. Ошибка создания ссылки сохраняется в `link_error`; URL не выдумывается. `unresolved` содержит `product_id`, причину и `recipe_ids`. Если при редактировании продукт отсутствует в справочнике, `product_id=null`, а причина содержит его название; новая запись не создаётся.

Частичный результат сам по себе не запускает повтор. Если пользователь уже разрешил замены или другую фасовку и есть конкретное ещё не выполненное изменение, агент может продолжить через `edit_cart` без повторного согласия, в пределах общих лимитов хода. Безрезультатный подбор с теми же условиями и данными не повторяется. Если продолжить в рамках поручения нельзя, агент показывает найденную часть, доступную ссылку и нерешённые потребности. Обязательной дословной формулировки ответа нет.

`edit_cart` загружает всю корзину и использует отдельный редактор CartRevision: products, unresolved, limits. В requested_sku_id каждой позиции редактор сохраняет фактически выбранный SKU исходной корзины либо явную замену из request. Новые SKU заранее выбирает разговорный агент. Повторный поиск и пакетный выбор всех SKU не запускаются. Для новых нормализованных продуктов по названию редактору передаются текущие продукты, явно указанные существующие product_id и до 10 кандидатов локального FTS-поиска. Это кандидаты, а не доказательство семантического соответствия; неизвестное название остаётся unresolved, новые продукты не создаются. Backend получает сведения SKU из кэша или исходной корзины, пересчитывает упаковки/цену и сохраняет полную версию. Исходный план и предыдущая корзина не изменяются.

`search_products` и `get_product_analogs` возвращают кандидатов SKU с названием, фасовкой, ценой и доступными ссылками. Они не меняют корзину. Аналоги запрашиваются по `sku_id`, а не по общему `product_id`. Результаты обоих поисков сохраняются в кэше по sku_id. Конкретная замена выполняется через `edit_cart`; модель не переписывает цену или фасовку.

## Результат и побочные эффекты

Общая форма результата:

| Поле | Содержание |
| --- | --- |
| `status` | `ok`, `needs_revision`, `partial` или `error` |
| `data` | Результат операции с ID и фактическим состоянием |
| `issues` | Замечания только четырёх разрешённых типов |
| `error` | Техническая ошибка или `null` |

- `ok`: операция выполнена. Для плана это прохождение согласованных четырёх проверок, не универсальная проверка всех пожеланий.
- `needs_revision`: результат требует исправления; доступные черновик и замечания возвращаются агенту.
- `partial`: сохранена корзина с нерешёнными позициями или недоступной ссылкой. Полноту состава показывает `total_is_complete`, причину отсутствия ссылки — `link_error`. Стоимость найденной части не доказывает соблюдение бюджета полной покупки.
- `error`: операция не завершилась успешно из-за аргументов, доступа, получения данных, модели или интеграции. Агент сообщает фактическое состояние, а не выдумывает успех.

Повторная доставка одного вызова записи не создаёт второй план или корзину. Ключ операции ведёт runtime. Отдельный пользовательский запрос на изменение — новая операция.

## Ровно четыре проверки качества

| Код | Проверка | Основание |
| --- | --- | --- |
| `RECIPE_NOT_FOUND` | Выбранный `recipe_id` существует | Каталог рецептов |
| `INVALID_NUMBER` | Значение имеет ожидаемый числовой формат и является конечным числом; количество порций строго больше нуля | Формат и допустимый диапазон числового поля |
| `DIFFICULTY_EXCEEDED` | Сложность выбранного рецепта не выше переданного предела | `limits` текущей операции |
| `BUDGET_EXCEEDED` | Рассчитанная стоимость укладывается в переданный бюджет с разрешённым отклонением | Явно заданные условия бюджета |

Для плана бюджет проверяется по средней оценке ингредиентов, для полной корзины — по выбранным упаковкам. `budget_rub` содержит исходную сумму из запроса/анкеты. Код проверяет верхнюю границу `round(budget_rub × 1.05, 2)`; меньшая стоимость допустима. Агент не прибавляет погрешность и не спрашивает разрешение на неё. В `limits` сохраняется исходная сумма, в `issues.expected` — допустимая граница. Даже найденная часть корзины может превысить бюджет — тогда возвращается замечание, а полнота покупки отдельно отражена в `total_is_complete`.

Нулевая или отрицательная порция получает INVALID_NUMBER и не участвует в расчёте КБЖУ и стоимости. Положительные дробные порции допустимы; достаточность порции код не оценивает. Проверка диапазона выполняется в evaluate, поэтому результат с оставшимися замечаниями после одной коррекции можно сохранить и прочитать как needs_revision. КБЖУ рассчитываются, но не сравниваются с целевыми нормами. Проверки полноты дней и приёмов пищи, аллергенов, предпочтений, разнообразия и семантической совместимости не добавляются. LLM-верификатора нет.

Проверка схемы вызова, существования адресуемого объекта и прав доступа нужна для исполнения API; она не вводит новые критерии качества меню.

## Обратная связь и исправление

Замечание содержит `code`, `path`, `message`, `actual`, `expected`, `requirement_source` и `repair_scope`. Код относится к одному из четырёх типов; сообщение по-русски объясняет конкретную ошибку. `expected` ссылается на данные каталога, числовой формат либо явно переданные ограничения, а не на придуманную норму.

Внутренний генератор получает текущий результат, исходный контекст, неизменные ограничения и конкретные замечания. После одной попытки исправления код повторяет расчёты и те же проверки. Оставшиеся замечания возвращаются вместе с черновиком. При `needs_revision` агент возвращает доступный результат и кратко объясняет указанные причины. Он не обходит предел коррекции повторной генерацией или самостоятельным поисковым построением того же плана; изменения предлагает только в рамках разрешённых пользователем условий.

Каждая запись создаёт новую версию с новым ID и `parent_id`. Успешная старая версия остаётся неизменной; `list` возвращает также черновики и версии. Квитанция операции сохраняется атомарно с объектом в SQLite.

## Точные типы и границы

- `PlanLimits`: обязательные `max_difficulty: easy | intermediate | advanced | null` и `budget_rub: number | null`.
- `CartLimits`: обязательное `budget_rub: number | null`. Сам объект limits обязателен при создании и в содержимом сохранённой версии; в аргументах edit его нет. Бюджет передаётся без прибавки погрешности.
- Числа порций, цены и КБЖУ конечные; строки и boolean не подменяют числовые значения. Количество порций строго положительное; достаточность порции кодом не оценивается.
- Поиск рецептов, товаров и аналогов возвращает до 10 кандидатов без аргумента размера. Списки планов и корзин — без ограничений выдачи и без аргументов.
- `source` — discriminated union `plan | recipes | skus`. `request` по умолчанию пустой; это буквальное поисковое уточнение каждого ингредиента для plan/recipes, не инструкция изменения покупки.
- Ошибка MCP аналогов: `ANALOGS_UNAVAILABLE`. Другие ошибки каталога: `CATALOG_UNAVAILABLE` либо `link_error` внутри сохранённой корзины.
- Ответ генератора содержит только `meals` и `explanation`. При отсутствии подходящего меню модель объясняет это словами; отдельного флага возможности нет. `ok` сообщает о выполнении операции и отсутствии замечаний четырёх проверок, не гарантирует полноту или смысловое соответствие.
- Не более двух внутренних вызовов на генерацию меню или одну операцию редактирования, включая ошибки формата. Ошибка Pydantic/native schema расходует ту же единственную возможность коррекции.


## Данные корзины и внутренние вызовы

Корзина: `cart_id`, `parent_id`, `status`, `source`, `limits`, `products`, `items`, `unresolved`, `subtotal_rub`, `total_is_complete`, `cart_url`, `link_error`. Поля произвольных заметок нет.

- `products`: `product_id`, `amount` в единице справочника, `recipe_ids` и необязательный `requested_sku_id`. Это позиции корзины, не самостоятельный справочник потребностей; отдельного ID строки нет.
- `items`: `product_id`, `sku_id`, выбранный `product` (карточка SKU), `packages`. Для прямого выбора product_id=null, а product=null, если карточки нет в кэше. У прежних записей sku_id находится в product.sku_id.
- `unresolved`: `product_id` либо null для неизвестного названия, `recipe_ids`, `reason`.
- Для skus цена складывается только по известным карточкам; subtotal_rub=null, если ни одной цены нет. total_is_complete=false также означает неизвестную цену. Пустой products здесь нормален, ингредиенты не выдумываются.
- `Selection`: `choices` с `product_id`, выбранным `sku_id` либо null и `reason`.

Структура самого нормализованного продукта и рецепта описана в [данных](data-model.md). Агрегация суммирует один product_id, сохраняет связь с рецептами и не считает неизвестное количество нулём. Конфликт явно выбранных SKU одного продукта возвращает `INVALID_CART_PRODUCTS`.

## Общая память

`update_memory(text)` принимает полную новую редакцию короткого свободного текста. Вход не содержит пользователя или версии: их задаёт runtime. Сохраняются только явно сообщённые устойчивые факты, полезные для питания, приготовления и покупок; не сохраняются временные условия, догадки, копия анкеты и случайные темы.

Явное устойчивое изменение заменяет прежний факт без отдельной команды забыть; уточнение исправляет смысл существующей записи. По просьбе пересмотреть память агент показывает актуальные сведения и применяет сообщённые исправления. Просмотр без исправлений не требует вызова `update_memory`. Повторы объединяются при необходимом обновлении, остальные факты сохраняются. Память не удаляется по давности; отдельная фоновая очистка не вводится. Явная просьба запомнить может ссылаться на понятный контекст текущего диалога.

Пустой текст очищает память. При совпадении версии результат содержит новую `memory` и `memory_revision`. При конфликте возвращаются `status=error`, `MEMORY_CONFLICT` и актуальная редакция в `data`, с которой агент объединяет изменение. Повтор уже выполненного вызова идемпотентен. Забывание не удаляет историю; старые сообщения не являются основанием записать факт обратно.

## Полные версии редакторов

- `PlanRevision`: полный список `meals`, `days`, `limits`, `explanation`.
- `SkuCartRevision`: все items как sku_id/packages и limits для корзины с source.type=skus. Тот же отдельный редактор, без каталога, поиска и повторного подбора.
- `CartRevision`: полный список `products` с выбранными `requested_sku_id`, `unresolved` в существующем формате `{product_id, recipe_ids, reason}`, `limits`.
- На входе — `current_plan` либо `current_cart`, `request`; корзине дополнительно доступны небольшой справочник продуктов и карточки явно упомянутых известных SKU. При коррекции добавляются `candidate`, `feedback`, `fixed_limits`.
- reasoning low; одна правка и не более одной коррекции, в том числе формата. После форматной ошибки доступна только одна оставшаяся попытка. Коррекция не выполняет поиск и не ослабляет limits.
- Служебные поля, вычисляемые итоги и ссылки не являются результатом модели. Прежняя ссылка не переносится в новую версию после отказа интеграции.
- Неизвестный SKU и недостаточная фасовка остаются unresolved. Ссылка для найденной части создаётся один раз после коррекции; ошибка ссылки отражается в link_error.
- Сохранность незатронутого содержимого и соответствие тексту задаются промптом и проверяются сценариями; схема и четыре проверки сами по себе не гарантируют семантику.

Товарные операции подключены к публичному MCP без авторизации. sku_id соответствует native id из поиска; создание ссылки передаёт `{id, q}`. [Точный транспорт и ограничения](vkusvill.md).
