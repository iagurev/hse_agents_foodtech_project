# Продуктовые решения

Октябрь 2026 · Основной документ: [продукт и границы MVP](../design/product.md).

## Диалог и персонализация

- Пользователь свободно обсуждает питание и поручает действия одному агенту. Обязательного сценарного маршрута нет.
- Несколько чатов имеют общую анкету и короткую свободнотекстовую память; история и временные исключения относятся к своему чату.
- Память содержит явно сообщённые устойчивые сведения. Изменение заменяет прежний факт, разовое условие не становится постоянным. Просмотр, правка и очистка доступны пользователю; фоновой очистки нет.
- Основные поля анкеты обязательны. Активность, бюджет, сложность и ограничения находятся на втором, пропускаемом шаге.
- Для полного рациона код даёт исходный ориентир энергии по физическим данным и активности. Агент подбирает меню под цель и диалог; явные числовые пожелания имеют приоритет. Пропуск активности не блокирует подбор.

## Меню и поиск

- Генератор получает весь каталог компактных рецептов. Отдельный уровень «блюдо» и обязательное summary не нужны.
- Выбор учитывает состав, сложность, время, технику, КБЖУ, стоимость и предпочтения. Количества и показатели относятся к одной базовой порции.
- Поиск возвращает до 10 карточек. Условия передаются явно в `limits`; backend не извлекает их из фразы и не наследует анкету. Во вкладке рецептов поиск глобальный, отдельно доступны блюда из планов.
- При создании агент передаёт исходный бюджет, код допускает превышение до 5%. Для полного меню ориентир из месячной анкеты — верхняя граница диапазона / 30 × число дней; указания диалога важнее.
- При редактировании действуют условия объекта до явного изменения в поручении. Сохраняется полная новая версия. Код проверяет только ID рецепта, числовой формат, сложность и бюджет; отдельного LLM-верификатора нет.
- КБЖУ меню показываются в среднем за день, стоимость — за весь план. Расход ингредиентов и покупка упаковок считаются отдельно.

## Данные и покупки

- Подготовка рецептов и продуктов отделена от диалога. Источники, метод расчёта и пометка оценки сохраняются; справочные КБЖУ и коэффициенты единиц допустимы с указанием происхождения.
- Рецепты используют существующие нормализованные продукты. Существенные виды сырья разделены; количества находятся в ингредиентах, шаги описывают приготовление.
- Покупка создаётся из плана, рецептов с порциями либо готовых товаров с количеством. Совместимые ингредиенты агрегируются до поиска; буквальный `request` уточняет поиск каждого продукта.
- Кандидаты MCP дополняются точными связями каталога. Свежие сведения MCP при совпадении товара приоритетны. Для расчёта используются подтверждённые фасовки и коэффициенты.
- План и покупка независимы. Правка покупки сохраняет незатронутые товары. Большой список остаётся одним объектом с несколькими ссылками по 30 разных товаров; ссылка не оформляет заказ.

## Интерфейс

- Телефонный веб-интерфейс без рамки: Чат, Планы, Рецепты, Покупки; настройки из шапки.
- Действия из карточек показывают понятный текст и названия, идентификаторы передаются отдельно. Если агент открыл рецепты, чат показывает его итоговую подборку.
- Ручные порции и количества пересчитываются сразу; сохранение создаёт версию. Название действует на всю цепочку, скрытие сохраняет доступ из прежних карточек.
- Показываются реальные этапы и общее время ответа. Reasoning и технические JSON остаются на сервере.
- Ориентир нагрузки — до пяти запросов в день и до $20 в месяц на LLM.
